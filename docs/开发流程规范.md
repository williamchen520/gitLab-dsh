# 开发流程规范：架构即代码（v2 模板）

> 状态：**默认开发规则**（与 `.dsh_rules` 规则 0 配套）
> 真理源：`ARCHITECTURE.json`
> 工具：`scripts/validate_arch.py`（HTTP 形状）、`scripts/validate_mcp.py`（MCP 清单）、`scripts/check_traceability.py`（计划→契约→测试对账）
> 模板：`docs/templates/`（计划书、决策记录、追溯矩阵）

本规范可以整份复制到新项目，改三处即可用：真理源文件名、校验命令、目录约定。

---

## 1. 铁律

```text
1. 新增 / 修改 / 删除路由或工具，先输出拟修改 JSON + 原因
2. 等人类明确回复“批准修改”
3. 收到批准后才写 ARCHITECTURE.json
4. 立刻运行 validate_arch.py（HTTP）+ validate_mcp.py（MCP）
5. 校验通过后，才写实现代码
6. 写完后再次运行两个校验器 + 全量测试
```

违反即视为架构漂移，不进入评审。

测试失败若因代码与 JSON 不一致：

```text
改代码适配 JSON
禁止反向改 JSON 参数来跑通测试
```

---

## 2. 校验分两层：形状与语义

**形状校验**（已有，机器强制）：

```text
validate_arch.py   JSON 路由/方法集合 == 应用路由集合；参数、路径变量一致
validate_mcp.py    server.py 的 @mcp.tool() == JSON mcp.tools；层计数一致
```

**语义校验**（新增，必须补）：形状对不代表行为对。每条关键不变量都要有一条可执行断言，放进测试或校验脚本：

| 不变量类型 | 断言形式 | 落点 |
|---|---|---|
| 只追加（judgement / 评审 / 决策） | 不存在 update 路径；重复写产生新行 | 单元测试 / DB 约束 |
| 不可变（快照、版本） | 修改后哈希变化即失败；旧行不可改 | 测试 |
| 状态机（claim / 策略） | 非法迁移抛错 | 测试 |
| 幂等（同 key 重复调用） | 两次调用返回同一实体 | 测试 |
| 截止条件（预算/上限） | 超限即 error，不静默截断 | 测试 |

规则：**一条不变量 = 一条测试**，测试名里带不变量编号（如 `test_inv_append_only_judgement`）。

---

## 3. 标准循环

```text
讨论（重大调整）
  → 决策记录（结构化，见 §4）
  → 拟修改 JSON（等“批准修改”）
  → 改 ARCHITECTURE.json + 两个校验器
  → 计划书（含验收标准 + 追溯条目）
  → 执行（小步 diff）
  → 门禁（见 §6：失败阻断，不是“记录一下”）
  → Worklog + 提交（需要时带 [APPROVED_BY_HUMAN]）
  → PR Pending Review，等“批准合并”
```

## 4. 决策记录

每次**架构级或不可逆**的选择（新增实体、改语义、删节点、换存储、定阈值）必须留一条决策记录。

格式（模板见 `docs/templates/决策记录.md`）：

```json
{
  "id": "D-7",
  "date": "2026-11-05",
  "status": "accepted",
  "options": ["A: ...", "B: ...", "C: ..."],
  "chosen": "B",
  "rejected_because": {"A": "...", "C": "..."},
  "impact": ["路由", "存储", "兼容性"],
  "owner": "human"
}
```

规则：

```text
决策记录写在 docs/decisions/（或 ARCHITECTURE.json 的 decisions 数组）
写入 JSON 的 decisions 需要“批准修改”；写在 docs/ 不需要
没有决策记录的语义变更，不得进入实现
```

> 落地到 `ARCHITECTURE.json.decisions` 属于 JSON 变更，需先批准；在批准前，决策先落 `docs/decisions/`。

## 5. 计划书与追溯矩阵

计划书写“做什么、怎么验收”，追溯矩阵写“每条验收对应契约的哪一条、哪条测试”。

计划书必须包含（模板见 `docs/templates/计划书.md`）：

```text
1. 目标（一句话）
2. 不做什么（范围守卫）
3. 验收标准（可执行，不是“看起来对”）
4. 契约变更（有无；需不需要“批准修改”）
5. 测试清单（文件名 + 用例名）
6. 风险与回滚
7. 未完成项
```

追溯矩阵（`plans/<plan-id>.traceability.json`，模板见 `docs/templates/追溯矩阵.md`）：

```json
{
  "plan_id": "2026-11-05-judgement-p1",
  "items": [
    {
      "id": "P1",
      "contract": {"rule": "/snapshots/{snapshot_id}/judgements", "endpoint": "judgements.create", "methods": ["POST"]},
      "test": "tests/test_judgement.py::test_http_endpoints_record_and_list",
      "status": "implemented"
    }
  ]
}
```

门禁命令：

```text
python scripts/check_traceability.py plans/<plan-id>.traceability.json
```

规则：

```text
计划里承诺的每一项，必须在矩阵里有一条
矩阵里的 contract 必须能在 ARCHITECTURE.json 找到
矩阵里的 test 必须真实存在（文件 + 函数名）
三者对不齐 -> exit 1 -> 不得提交
```

---

## 6. 门禁语义（通过与不通过）

“通过与不通过的命令”必须是**阻断式**，不是提示式：

```text
通过（全部 exit 0）：
  python scripts/validate_arch.py ...
  python scripts/validate_mcp.py ...
  python scripts/check_traceability.py plans/<id>.traceability.json
  pytest -q

不通过（任一 exit != 0）：
  停止提交；回到讨论或修复
  禁止 --skip / 注释校验 / 改契约迁就测试
```

强制落点（至少两个）：

```text
1. 本地钩子：.githooks/pre-commit 跑形状校验（快）
2. CI：跑全量测试 + 追溯对账（慢）
```

钩子只防误操作，CI 才是强制边界。

---

## 7. 校验器规则

```text
validate_arch.py
  - JSON route + method 集合 == 应用路由集合
  - endpoint 函数存在；路径变量与声明参数在签名中
  - 重复 route+method 报错
  - status=planned 允许暂不实现

validate_mcp.py
  - server.py 每个 @mcp.tool() 都在 mcp.tools
  - 每个 mcp.tools 都在 server.py
  - layers.shells[mcp].tools == 声明条数
```

基线以**当前仓库实际结果**为准，不在文档里硬编码数字（历史上写死过 202、735，都过期了）。

## 8. 生成器（legacy）

`scripts/scaffold_from_arch.py` 属于早期 Flask 项目；新项目不强制使用。若要保留：

```text
只接受 status=planned 且带 codegen.id 的节点
只生成到 generated/<id>/，不自动注册
不修改已有入口文件
```

---

## 9. MCP 约束

```text
MCP 是薄转发层：不 import services/*，不 import 应用入口
只通过统一的 _call 转发 HTTP 路由
工具名、参数名与 JSON mcp.tools 一一对应
```

---

## 10. 授权指令

```text
“批准修改”  只授权改 ARCHITECTURE.json
“批准合并”  只授权 merge
“合并”“可以”“LGTM”“CI 通过” 都不算授权
```

---

## 11. 物理拦截

```text
.githooks/pre-commit    staged JSON 合法 + 形状校验
.githooks/commit-msg    staged JSON 时，message 必须含 [APPROVED_BY_HUMAN]
安装：git config core.hooksPath .githooks
```

`--no-verify` 可绕过，所以 CI 必须再跑一遍同样的校验。

## 12. Worklog

```text
worklogs/YYYY-MM-DD-<topic>.md
1. 需求
2. 契约变化（含决策记录 id）
3. 修改文件
4. 业务逻辑变化
5. 校验结果（arch / mcp / traceability）
6. 测试命令与结果
7. 风险 / 外部 API
8. 未完成项
```

---

## 13. PR 与重大重构

```text
创建后       Pending Review
收到“批准合并” merge
否则         不得 merge / squash / rebase

净变更 <= 300 行   正常 PR
净变更 >  300 行   标题加 [LARGE]，不自动合并
```

PR 描述必须包含：修改模块、业务变化、测试结果、追溯矩阵链接、风险、净变更行数。

---

## 14. 离线降级

云端断服、降级到本地小模型时：

```text
禁止写代码、禁止改 JSON、禁止重构、禁止 migration
只允许摘要 / 意图识别 / 闲聊
用户要求写代码时直接拒绝并说明
```

理由：小模型不具备稳定施工能力；断服期改动会绕过校验与人工审批，恢复后无法判断可信基线。
