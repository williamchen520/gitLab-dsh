## 1. 项目概述

### 1.1 一句话定位

以「实验」为记录单元、以 **Git 式快照**管理版本演进的本地优先实验记录系统。

### 1.2 目标

| 编号 | 目标 |
|---|---|
| G1 | 记录实验的过程、参数、结果与附件，形成可追溯的完整链路 |
| G2 | 每次记录可固化为不可变快照，任意时刻可回溯、对比、导出 |
| G3 | 本地优先：数据留在本机，无需服务端即可完整工作 |
| G4 | 一套内核，两种外壳：可嵌入 DSH 作为插件，也可独立为桌面应用 |

### 1.3 非目标（当前阶段）

- 不做多人实时协同编辑
- 不做云端托管服务
- 不做通用 Git 客户端（不追求与 `git` 命令完全兼容）
- 不做仪器直连与实验室硬件集成

## 2. 核心概念与领域模型

### 2.1 概念

| 概念 | 说明 |
|---|---|
| **Project** | 项目，实验的顶层容器，对应一个记录库 |
| **Experiment** | 实验，最基本的记录单元，承载目标、假设、参数 |
| **Run** | 一次执行。同一实验可多次运行，各自独立留痕 |
| **Step** | 运行中的步骤，记录操作、观察、耗时 |
| **Artifact** | 产物：数据文件、图表、日志、图片 |
| **Snapshot** | 快照。某一时刻全部内容的不可变固化，带父指针形成 DAG |
| **Branch** | 分支标签，指向某个快照，用于并行探索 |
| **Tag** | 里程碑标记，如 `v1.0`、`published` |

### 2.2 关系

```text
Project 1─n Experiment 1─n Run 1─n Step
                  │              │
                  └── n Artifact ┘
                  │
                  └── n Snapshot ──(parent)──> Snapshot ...

Snapshot n─n Artifact      # 快照固化了当时可见的产物集合
Branch ──> Snapshot        # 分支只是一个可移动的指针
Tag    ──> Snapshot        # 标签是不可移动的指针
```

**关键约束**：快照一旦创建即不可变。修改只能产生新快照，历史永不改写。这条是整套系统可信度的地基，与 `ARCHITECTURE.json` 只读原则同源。

## 3. Git 式快照：语义取舍

这是本项目最需要先想清楚的部分。Git 的完整语义放到实验记录上是过重的，必须裁剪。

### 3.1 借鉴什么

| 借鉴 | 理由 |
|---|---|
| **内容寻址**（SHA-256） | 同一份数据只存一次，天然去重，篡改可检测 |
| **DAG 父指针** | 快照历史形成有向无环图，回溯路径唯一 |
| **不可变对象** | 审计与复现的基础 |
| **分支 = 可移动指针** | 并行实验路线，成本极低 |
| **快照 = 全量树** | 取用简单，不依赖重放补丁 |

### 3.2 不借鉴什么

| 舍弃 | 理由 |
|---|---|
| **三路合并与冲突解决** | 实验记录没有"同一行文本被两人改动"的场景，合并语义无意义 |
| **变基 / 改写历史** | 与不可变性直接冲突 |
| **暂存区（staging）** | 记录是连续书写，分步暂存是负担 |
| **文本 diff** | 实验数据多为二进制，diff 无意义；改为**元数据 diff + 产物清单 diff** |

### 3.3 分支的替代方案

实验的"分叉"更接近**派生实验**而非代码分支：

```text
方案 A：轻分支（纯指针）
  从快照 S 派生分支 exp-2，两者永不合并，各自演进。
  优点：实现极简；缺点：汇合处只能靠人工标注关联。

方案 B：派生子实验
  从实验 E 派生新的实验 E'，携带来源指针 derived_from=E@S。
  优点：语义贴近科研直觉（对照组/实验组）；缺点：需要额外的关联视图。
```

**建议 D-1 采用 B**，因为它把"分叉"落在领域模型上，而不是版本控制模型上。待决。

## 4. 存储设计

### 4.1 分层

```text
┌─────────────────────────────────────────────┐
│ 元数据层：SQLite                            │
│   实验、运行、步骤、快照、指针、标签         │
│   体积小、可事务、可查询                    │
├─────────────────────────────────────────────┤
│ 对象层：内容寻址文件库（CAS）                │
│   blobs/sha256/ab/cdef...                   │
│   每个对象只存一份，按哈希分桶                │
├─────────────────────────────────────────────┤
│ 工作区：正在编辑的草稿                       │
│   可选：直接编辑 CAS 副本，提交时固化         │
└─────────────────────────────────────────────┘
```

### 4.2 为什么不直接用 Git

| 方案 | 评价 |
|---|---|
| 调 `git` 命令 | 二进制体积大、跨平台路径问题多、异常态难处理 |
| libgit2 / pygit2 | 依赖原生库，插件与桌面双形态打包复杂 |
| **自建 CAS + SQLite** | 无外部依赖、语义可控、导出口径自定 ✅ |

结论：**借鉴模型，不依赖 Git 实现**。导出时可生成标准 `.eln`（zip + RDF）或纯目录树。

### 4.3 大文件策略

实验产物的常见形态是几百 MB 的原始数据。策略：

- 单文件超过阈值（默认 256 MB）不做内容寻址复制，改存**引用记录**（路径 + 哈希 + 大小 + 修改时间），快照只固化引用；
- 阈值可配置，`D-2` 待定。

## 5. 系统架构

### 5.1 分层

```text
┌───────────────────────────────────────────────┐
│ 外壳层（三选二，可同时存在）                    │
│  ① Flask Web UI（本地浏览器访问）              │
│  ② 桌面壳（Tauri / pywebview 内嵌同一前端）    │
│  ③ DSH 插件（待确认接入方式，见 D-3）          │
├───────────────────────────────────────────────┤
│ 接口层：Flask API（REST，本地端口）            │
├───────────────────────────────────────────────┤
│ 核心层 core（纯 Python，禁止 import flask）     │
│   domain/   领域模型与校验                     │
│   snapshot/ 快照引擎（哈希、DAG、diff）        │
│   store/    SQLite 元数据 + CAS 对象库         │
│   io/       导入导出（.eln / 目录树 / JSON）   │
└───────────────────────────────────────────────┘
```

**架构铁律**：`core` 不得依赖任何 Web 框架。这条是双形态能成立的前提——DSH 插件和桌面应用只是不同的外壳，共用同一个内核。

### 5.2 双形态的落地方式

| 形态 | 启动方式 | 说明 |
|---|---|---|
| 独立桌面 | 双击 → 本地起 Flask（随机端口）→ 内嵌浏览器窗口 | 用户无感 |
| DSH 插件 | 由 DSH 拉起同一进程，UI 以插件面板呈现 | 需确认 DSH 的插件加载与进程模型（`D-3`） |
| 纯 Web | `python -m exprec serve` | 调试与自托管用 |

三者共用 `core` 与 Flask API，仅外壳不同。

## 6. 数据模型（草案）

```sql
-- 项目
project(id, name, description, created_at)

-- 实验
experiment(id, project_id, title, hypothesis, status, derived_from_snapshot_id, created_at)

-- 运行
run(id, experiment_id, seq, started_at, ended_at, status, params_json)

-- 步骤
step(id, run_id, seq, action, observation, duration_s, created_at)

-- 产物
artifact(id, run_id, path, blob_hash, size, mime, created_at)

-- 快照（不可变）
snapshot(id, experiment_id, parent_id, message, author, created_at, tree_hash)

-- 快照内容（固化当时的产物清单）
snapshot_item(snapshot_id, path, blob_hash, size, mime)

-- 指针
branch(id, experiment_id, name, snapshot_id)
tag(id, snapshot_id, name, created_at)

-- 对象库索引
blob(hash PRIMARY KEY, size, refcount, created_at)
```

`tree_hash` 由 `snapshot_item` 的 `(path, blob_hash)` 排序后计算，保证同样内容得到同样哈希。

## 7. API 设计（草案，待写入 ARCHITECTURE.json）

按 `scripts/validate_arch.py` 的契约格式，节点长这样：

```json
{
  "rule": "/api/experiments/<int:experiment_id>/snapshots",
  "endpoint": "snapshots.create",
  "methods": ["POST"],
  "status": "planned",
  "parameters": ["message", "author"],
  "codegen": {
    "id": "snapshots_create",
    "blueprint": "snapshots",
    "function": "create_snapshot",
    "mcp_server": "search_server",
    "mcp_tool": "create_snapshot",
    "description": "Create an immutable snapshot of the experiment.",
    "parameters": [
      {"name": "experiment_id", "in": "path", "type": "int"},
      {"name": "message", "in": "body", "type": "string"}
    ]
  }
}
```

初步端点清单（`status` 全部先标 `planned`）：

| 分组 | 端点 |
|---|---|
| 项目 | `GET/POST /api/projects` |
| 实验 | `GET/POST /api/experiments`、`GET /api/experiments/{id}` |
| 运行 | `POST /api/experiments/{id}/runs`、`POST /api/runs/{id}/steps` |
| 产物 | `POST /api/runs/{id}/artifacts`（上传） |
| 快照 | `POST /api/experiments/{id}/snapshots`、`GET .../snapshots`、`GET /api/snapshots/{id}` |
| 差异 | `GET /api/snapshots/{a}/diff/{b}` |
| 导出 | `GET /api/experiments/{id}/export` |

## 8. 与开发规则骨架的衔接

本项目**直接继承**本仓库的规则层，一个环节都不改：

1. `.dsh_rules` 规则 0：先输出拟修改的 `ARCHITECTURE.json`，等「批准修改」
2. commit message 带 `[APPROVED_BY_HUMAN]`，由 `.githooks/commit-msg` 物理拦截
3. `python scripts/validate_arch.py` 通过后才写路由
4. 新节点先 `planned`，用 `scaffold_from_arch.py` 生成骨架

**需要同步改造的两处**（因为规则层脚本是 Flask 硬耦合的）：

| 文件 | 问题 | 改造 |
|---|---|---|
| `scripts/validate_arch.py:130` | 硬编码 `import api_server` | 改为可配置的应用入口 |
| `scripts/scaffold_from_arch.py` | 只生成 Flask Blueprint | 增加 `--target=flask\|mcp`，本项目先只用 flask |
