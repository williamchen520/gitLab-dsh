# 02 · 计划与追溯

## 为什么先写计划

没有计划，“做完了”只是感觉；有计划，才能把“说到的”逐条对到契约和测试上。

## 计划书

放在 `plans/<plan-id>.md`，模板见 `docs/templates/计划书.md`。必须包含：

```text
1. 目标（一句话）
2. 不做什么（范围守卫）
3. 验收标准（可执行条目，编号 P1、P2…）
4. 契约变更（有无；是否需要“批准修改”）
5. 测试清单（文件 + 用例名）
6. 风险与回滚
7. 未完成项
```

验收标准写成**可判定**的：

```text
✅ P1  POST /snapshots/{id}/judgements 返回 201，body 含 judgement.id
✅ P2  同一 criteria 重复提交返回同一 id
❌ P3  体验流畅、结果正确
```

## 追溯矩阵

`plans/<plan-id>.traceability.json`，模板见 `docs/templates/追溯矩阵.md`：

```json
{
  "plan_id": "2026-11-05-judgement-p1",
  "items": [
    {
      "id": "P1",
      "contract": {
        "rule": "/snapshots/{snapshot_id}/judgements",
        "endpoint": "judgements.create",
        "methods": ["POST"]
      },
      "test": "tests/test_judgement.py::test_http_endpoints_record_and_list",
      "status": "implemented"
    }
  ]
}
```

规则：

```text
计划里的每条验收 → 矩阵里一条
矩阵里的 contract → 必须能在 ARCHITECTURE.json 找到
矩阵里的 test     → 文件存在 + 函数存在
status=implemented 不许缺 test
```

## 对账命令

```bash
python scripts/check_traceability.py plans/<plan-id>.traceability.json \
  --tests-root ../dsh-snapshot      # 代码仓库根目录
```

- 全部对齐 → `traceability: N item(s) aligned`，exit 0；
- 任何一条不齐 → exit 1，并指名是哪一条、缺什么。

## 人读版本

```bash
python scripts/render_plan_md.py plans/<plan-id>.traceability.json
python scripts/render_plan_md.py plans/<plan-id>.traceability.json --check
```

生成同名 `.md` 表格（条目 / 契约 / 测试 / 状态），给评审看；**不要手改生成的 md**。

## 什么时候允许 planned

```text
接口先立契约、实现分两批落地时：status=planned 允许测试暂缺
但必须在计划书「未完成项」里写明，并在同一 PR 或紧随的 PR 里补齐
```

## 反模式

- 计划写了 A/B/C，矩阵只有 A：说明有两条没人负责；
- 矩阵里 test 是“以后补”：那就不是 implemented；
- 契约条目里 methods 写错一个：对账命令会直接报出来，不要手改矩阵绕过。
