# 04 · 提交与评审

## Worklog（先写，再提交）

路径：`worklogs/YYYY-MM-DD-<topic>.md`，必须包含：

```text
1. 需求
2. 契约变化（含决策 id）
3. 修改文件
4. 业务逻辑变化
5. 校验结果（arch / mcp / traceability / render）
6. 测试命令与结果
7. 风险 / 外部 API
8. 未完成项
```

Worklog 是给三个月后的自己看的，不是交作业：**“为什么这么改”比“改了哪些文件”重要。**

## Commit message

```text
feat: <做了什么>
fix: <修了什么>
docs: <文档>
arch: <契约>
chore: <杂务>

若本次 staged 了 ARCHITECTURE.json，message 必须含 [APPROVED_BY_HUMAN]
```

示例：

```bash
git commit -m "feat: judge snapshots against deterministic checks"
git commit -m "arch: add judgements endpoints [APPROVED_BY_HUMAN]"
```

## 一个提交一个主题

```text
✅ 一个功能 + 它的测试 + 它的契约条目 + 它的 worklog
❌ 功能 + 顺手重构 + 改格式 + 修无关 bug
```

## PR

```text
创建后        Pending Review
收到“批准合并” merge
未收到        不得 merge / squash / rebase
```

描述必须包含：

```text
- 修改模块
- 业务逻辑变化
- 测试结果
- 追溯矩阵链接
- 风险提示（外部 API / 数据写入 / 权限变化）
- 净变更行数
```

## 重大重构

```text
净变更 <= 300 行    正常 PR
净变更 >  300 行    标题加 [LARGE]，不自动合并，需专门评审
```

## 合并前自检

```text
[ ] 五个门禁命令全过
[ ] worklog 已写，含未完成项
[ ] 契约变更带 [APPROVED_BY_HUMAN]
[ ] 生成的 md 没有手改痕迹
[ ] PR 描述与追溯矩阵对得上
```

## 授权指令

```text
“批准修改”  只授权改 ARCHITECTURE.json
“批准合并”  只授权 merge
“合并”“可以”“LGTM”“CI 通过” 都不算
```
